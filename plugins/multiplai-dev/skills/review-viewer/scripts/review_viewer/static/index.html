            How a review runs

            The review skill runs these steps in order. Agents are separate model calls. The checks between them are code: they re-read the reviewed commit with git and call no model.

            1. Find. Several finder agents read the change, each looking for one kind of problem (see Finders). Each finding has a claim, a severity, a failure scenario and citations: lines of a file, with the text on them quoted exactly.
            2. Check the findings. Code drops a finding that repeats one already returned (same file, same first line, same opening words of the claim). It then rejects a finding when a quote is not on the lines it cites at the reviewed commit, when its first citation is a web page, when it is about a file the change did not touch (unless the finder reports it as a problem that was already there), or when its severity is unknown.
            3. Verify. A fresh agent checks each remaining finding on its own. It is given the finding and the lines it cites, not the diff, reads whatever settles the question, and answers confirmed, refuted or unverifiable, citing the lines it read. Unless it refutes the finding, it also writes one sentence on what correct behaviour would be.
            4. Check the verdicts. Code turns a confirmed answer into unverifiable when none of its citations is a quote found on the cited lines (a web page does not count). An unverifiable finding drops one severity step, but not below MEDIUM while it waits on something under Needs you.
            5. Merge. Code groups confirmed and unverifiable findings whose lines overlap, and one agent per group says which describe the same defect (see Merge groups).
            6. Repeats. When you rejected findings in an earlier round of this review, a finding with the same id is marked a repeat, and one agent says whether any other finding describes the same defect as a rejected one. With nothing rejected earlier, this step is skipped.
            7. Assess. One agent reads the findings together and labels each one (see labels). It can also merge duplicates the merge step missed. It is skipped when there is nothing to label, or only one finding and no earlier round.

            Repeats and Assess never delete a finding or change a verdict or a severity. A review of the same PR after new commits is a new round: the earlier round's findings and your decisions on them are kept.

            Finders

            A finder is one agent with one job. It reads a copy of the reviewed commit with read and search tools, and may look things up on the web. Five finders run on a change:

            diff-bugs
            Reads the diff and the changed files, and nothing else. Looks for bugs the change brings in: wrong conditions or values, missed cases, broken error handling, lost data.
            callers
            Opens what the changed code calls and what calls it. Looks for breakage at those boundaries, such as a changed signature or return shape, or a caller that relied on behaviour the change removed.
            history
            Reads the commit subjects, which say what the change is meant to do, and looks for code that does not do it, and for behaviour the removed lines had that nothing replaces.
            conventions
            Checks the changed lines against the repository's own rules: each coding-standards.md and CLAUDE.md from the repository root down to the changed files' folders. Also searches for docs and comments elsewhere that the change made wrong.
            tests
            Looks for changed behaviour that no test would catch breaking, and for added or changed tests that cannot fail: tests that compare a value copied from the code, read source code as text, or replace with a stub the very thing whose failure the code must handle.

            A review of a whole repository or folder, rather than a change, splits the files into groups and runs each finder once per group. The Checked tab names those runs diff-bugs@0, diff-bugs@1 and so on, counting groups from 0. history does not run there: there are no commits to compare with.

            The Checked tab

            Shown when the review wrote a record of its checks (checks.json, review 0.26 and later). It shows what every agent was given, did and concluded.

            Finders table

            One row per finder run.

            finder
            Which finder (see Finders).
            ran
            ran, or failed when the agent call failed; its entry under Agents says why.
            files read
            How many different files it opened with its read tool. Searches and web pages are not counted.
            returned
            How many findings it returned. The next four columns split them.
            kept
            Passed the check in code and went to a verifier, whatever the verifier then said, and was not merged into another finding.
            deduped
            Dropped before the check, because a finding with the same file, first line and opening words of the claim had already been returned, by this finder or another.
            merged
            Merged into another finding by the merge or assess step; the Findings table says which.
            rejected
            Failed the check in code; the Findings table names the rule.

            Findings table

            One row per finding a finder returned, deduped copies left out.

            finding
            Its id. It opens the finding on the Findings tab when the review still shows it; a finding merged into another is plain text.
            finder
            The finder run that returned it.
            verdict
            The verifier's answer, after the check in code: confirmed, refuted or unverifiable. failed when the verifier's call failed (the finding then counts as unverifiable); not verified when no verifier ran, as for a rejected finding.
            gate
            passed; rejected: and the rule when the check in code rejected it (quote not at cited lines, path not at head, empty quote, is not a changed file, no citations, first citation is a web source, unknown severity, or other); or lowered by verdict_gate when the verifier answered confirmed but cited nothing the check could find, so its answer became unverifiable.
            fate
            kept, merged into another finding's id, or rejected, as in the Finders table.

            Merge groups

            Two finders can report one defect in different words. Code links two confirmed or unverifiable findings when their anchors are in the same file and overlap or are at most 2 lines apart, or when a cited file range of one overlaps, or comes within 2 lines of, a cited range of the other in the same file. Web citations never link. Links chain: when A links to B and B to C, all three form one group. One agent reads each group of two or more and says which findings are the same defect.

            Of each set of duplicates one finding stays: a confirmed one before an unverifiable one, then the most severe, then the first. It keeps its id and verdict, takes the highest severity in the set, and gets the citations of all of them. The others leave the Findings tab, and their fate here reads merged into the one that stayed.

            group
            The ids of the findings in the group.
            outcome
            merged X into Y for each finding merged away, no duplicates, or failed when the agent call failed; that group then stays as it was.

            The section appears only when some findings overlapped.

            Agents

            One entry per agent call, in the order they started. Its heading names the step (find, verify, merge, repeats, assess), what the call was about (a finder run, a finding's id, a merge group's ids) and its outcome. Open it to see:

            Given
            What its prompt held: the diff, the commit subjects, the PR description, the branch rules, the rules files, or the finding to check.
            Tool calls
            Every file it read, search it ran and web page it fetched: what it asked for, never what came back. A read of a changed file opens in the code pane; a web address stays text, never a link.
            Findings returned, Verdict
            What it concluded, each citation marked as below.

            Each citation carries two marks. ⚠ flags one whose gate is fail or whose seen is not-seen.

            gate: pass
            Code found the quoted text on the cited lines at the reviewed commit (differences in spacing ignored).
            gate: fail
            It did not: the lines hold other text, the file is not in that commit, or the quote is empty.
            gate: web
            A web page. Code does not check it.
            seen: read
            The agent opened that file with its read tool, at a range that covers the lines, or the whole file.
            seen: searched
            It did not read those lines, but ran a search over that file or a folder holding it.
            seen: diff
            The lines were in the diff its prompt held.
            seen: prompt
            The lines were in its prompt another way: a verifier's prompt holds the lines the finding cites.
            seen: fetched
            A web citation whose page the agent fetched.
            seen: not-seen
            None of these: nothing shows the agent looked at those lines or fetched that page.

            Findings, verdicts and labels

            The Findings tab lists findings in three sections, Code, Tests and Docs, by the finding's topic (or, for an older review, a guess from its path), and by severity within each. Severity is read within its section: a HIGH under Tests is a serious test gap, not a serious defect in the code. Picking one moves the code to its lines and shows the claim, the failure scenario, the expected behaviour and the verdict's reason. When the Checked tab has the finding's verifier, a link opens its entry there, with every line it read and cited; otherwise the finding lists its cited code and the verifier's citations. Code starts open; Tests and Docs fold until you open them or pick a finding in them. Once the list scrolls out of sight, a bar under the tabs leads back to it, with Prev and Next.

            Accept, reject or defer a finding at the bottom of its page, or press ✓ or ✕ on it in the list (they show on hover). Deciding the open finding opens the next one that still needs a decision and scrolls back to the list; after the last, the finding page is empty. Accept all, beside the count, accepts every finding that still needs a decision, after you confirm; refuted and decided findings are left as they are. Hovering a badge shows what its word means. Each finding shows a status:

            confirmed
            The verifier showed the failure can happen, citing lines that code found at the reviewed commit.
            unverifiable
            It depends on something the verifier could not read, or the code does not settle it. Its severity was lowered one step.
            refuted
            The verifier showed it cannot happen. Hidden unless you tick Show decided and refuted, as is every finding you accept, reject or defer, so the list holds only what still needs a decision.
            rejected
            The check in code rejected it before any verifier saw it. Never shown on the Findings tab or counted; the Checked tab lists it with the rule that rejected it.

            The assess step's label shows as a badge. A finding without one was labelled useful, or the review is older than labels.

            repeat
            The same defect as a finding you rejected in an earlier round. Never shown or counted: your earlier rejection stands.
            still-open
            The same defect as an earlier-round finding you accepted, deferred or have not decided: it is not fixed yet.
            low-value
            True, but not worth acting on, for one of three reasons named at the start of its reason. [context]: the PR description, the commit subjects, a rules file or a note on an earlier decision says the affected thing does not matter. [covered]: fixing another finding fixes this one too. [speculative]: it fails only after a future change nobody has proposed, and the code is correct now; this does not apply when the change's own tests, comments or description promise to catch such a change. Never shown or counted.

            The verifier also labels each finding's topic, what it is about, which sets its section: tests and docs have their own, every other topic is under Code. A topic in italics was guessed from the file's path, for a review older than topics.

            code
            The behaviour of the program.
            tests
            A missing, weak or wrong test.
            docs
            Documentation, comments or decision logs.
            config
            Configuration: settings, flags, environment.
            infra
            Deployment, CI or cloud resources.
            data
            Schemas, migrations or stored data.
            security
            Who can reach or change what: access, secrets, injection.
            performance
            Speed, memory or cost at the size the code runs at.
            process
            The order of steps a person must follow, such as merge before deploy.

            The verifier also rates each finding's impact: what goes wrong in production if the change is merged as it is. It shows as a badge beside the topic. A review older than impact has none.

            breaks-users
            People who use the product see a failure, a wrong result, lost or exposed data, on a path they will take.
            breaks-business
            The company is harmed without a user necessarily seeing it: money lost or miscounted, a deploy or job that fails, access granted wider than intended, a record audits or billing rely on that is wrong, or a document that would lead an operator to a wrong action in production.
            correctness-only
            The code is wrong, but no path after merge reaches a user or the business: an edge case no caller reaches, a trap for the next change. Every missing or weak test is rated this.
            hygiene
            Nothing behaves wrongly: naming, dead code, a convention breached with no consequence, a stale comment that misleads nobody.

            A review run with --mode critical shows Critical only in the header and lists only breaks-users and breaks-business findings; the rest are in the review's markdown appendix.

            Gate-rejected, repeat and low-value findings stay in findings.json and in the review's markdown appendix; the page leaves them out of the list, every count, the code markers, Go to and the risk score. Accept, Reject or Defer records your decision; a later round of the review reads it.

            Needs you

            A tab of its own, shown when the review could not get something it needed. Items are grouped by what they block: the review as a whole first, then each finding, which links to it. Each item says what is missing; why (the review has no access, a lookup failed, or it is not reachable on the web); a command a person with access could run to get it, where to look when no one command gets it (a console page, a dashboard, a team), or both.

            When the review named neither, Ask the session puts a question about the item in the chat, for you to read and send.

            A verifier lists what kept it from settling its finding. A finder's gaps, and a failed GitHub lookup of the PR or its branch rules, block the review as a whole. A finding's own needs also show under it on the Findings tab.

            The page runs nothing: read a command before you run it. Code keeps a command only when it is one short line, has no pipes, redirects or chained commands, and is a known read-only form; otherwise the item shows where to look instead, when the review named a place.

            Run

            At the bottom of the Summary tab, for a review that recorded it (multiplai-dev 0.28 and later).

            Cost
            What the agent calls cost, against the review's spending ceiling.
            Tokens
            The total, then input, output, and cache reads and writes.
            Agent calls
            How many model calls the review made.
            Wall time
            How long the review ran, adding up each run when it was resumed. "Stopped by the budget and resumed" when the ceiling stopped it once.
            Errors
            How many problems the run noted, such as failed agent calls. Shown only when there were some.
            Model
            The model and effort each step used.
            Table
            One row per step (each finder, verify, merge and so on): calls, tokens, cost and time.

            With several reviews open, a line under it totals every review that recorded a run.

            Switch between unified and split
